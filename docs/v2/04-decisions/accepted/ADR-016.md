## ADR-016 — WF1 AI Quality Gate (Phase 2): เช็คเนื้อหาจริงก่อน publish ไม่ใช่แค่โครงสร้าง
**Date**: 2026-07-23 (session 29)
**Status**: Gate เดิม LIVE ตามบันทึกท้ายเอกสาร; policy amendment 2026-09-21 บันทึกแล้ว แต่ runtime revision ยังไม่ deploy/verify ในรอบนี้

### Amendment — 2026-09-21: แยกหัวข้อบทความออกจากข้อเสนอธุรกิจ

**สถานะ:** บันทึกข้อกำหนดตามคำขอ Product Owner ให้แก้ที่ ADR; ยังไม่ได้แก้หรือทดสอบ workflow ที่ active ใน n8n ในรอบนี้
**Policy revision:** `ADR-016/2026-09-21` ใช้แทนข้อความเก่าที่ตีความว่าห้ามกล่าวถึงการสร้างบ้านโดยรวม ประวัติการตัดสินใจเดิมด้านล่างเก็บไว้เพื่ออ้างอิง

#### เหตุผลและขอบเขตหลักฐาน

- Dashboard ที่ Product Owner ส่งมา: 47 decisions, ผ่าน 1 / บล็อก 46, ยืนยันแล้ว 47, ถูก 25 / ผิด 22, false positive 22 / false negative 0; accuracy = 25/47 = 53.2% ตาม feedback ชุดนี้
- ตัวเลขนี้ไม่ยืนยันความแม่นยำทั่วไปหรือประสิทธิผลของนโยบายใหม่ และยังไม่ได้ตรวจเนื้อหาเต็ม/เหตุผลระดับประโยคของทั้ง 47 รายการ สี่ชื่อเรื่องล่าสุดที่แสดงว่า “ยืนยันถูกต้อง” ต้องไม่ถูกเปลี่ยนเป็น “บล็อกผิด” จากชื่อเรื่องเพียงอย่างเดียว
- พบช่องว่างในข้อกำหนด: ADR-010 มีข้อความ “เลิกอ้างอิงรับสร้างบ้านทั้งหมด” และตัด keyword เกี่ยวกับงานก่อสร้าง ส่วน ADR-016 เดิมไม่มีขอบเขต educational content ชัดเจน จึงต้องแก้ความหมายต้นทางร่วมกับ Business Model; ยังไม่สรุปว่าเป็นสาเหตุของทุก execution โดยไม่มี active workflow และบทความเต็ม

#### ข้อตัดสินใจที่ใช้ต่อจากนี้

**Finnhouses ไม่รับสร้างบ้านให้ลูกค้า แต่เผยแพร่ความรู้เรื่องสร้างบ้านได้**

1. **หัวข้อที่อนุญาต:** ค่าใช้จ่าย/งบสร้างบ้าน, แบบบ้านและสไตล์, ขั้นตอนจ้างบริษัทรับสร้างบ้าน, การเลือกผู้รับเหมา, BOQ, วัสดุ, การตรวจงาน และรีโนเวท ใช้เพื่อให้ความรู้/การตลาดได้ ไม่ต้องเป็นบริการที่บริษัทขายทุกหัวข้อ
2. **บล็อก `brand_guardrail_violation` เมื่อเนื้อหาเสนอหรือทำให้เข้าใจว่า Finnhouses เป็นผู้รับเหมาสร้างบ้านให้ลูกค้า** เช่น รับจ้างก่อสร้าง, รับเหมาครบวงจร, จองคิวสร้างบ้านกับเรา, ขอใบเสนอราคาจ้างเราสร้างบ้าน รวมถึงการอ้างโดยนัยผ่าน “เรา/ทีมงานของเรา” ในบริบทรับจ้างก่อสร้าง
3. **บทบาทที่อนุญาต:** นายหน้า/ฝากขาย, ที่ปรึกษา/ตรวจสอบ, รีโนเวททรัพย์ของบริษัทเพื่อขาย และพัฒนาทรัพย์ของบริษัทเพื่อสร้างบ้านขาย ตาม Business Model ปัจจุบัน การพัฒนาทรัพย์ของตนเองไม่เท่ากับรับจ้างสร้างบ้านให้ลูกค้า
4. **ตัดสินจากบริบททั้งบทความและ CTA:** ชื่อเรื่อง, slug, category หรือการพบคำว่า “สร้างบ้าน/ผู้รับเหมา/งานก่อสร้าง/ของเรา” อย่างเดียวไม่เพียงพอสำหรับ brand violation อ่านว่าใครเป็นผู้ให้บริการและเสนออะไร คำปฏิเสธ ข้อความอ้างตัวอย่าง และการกล่าวถึงบริษัทภายนอกไม่ใช่ข้อเสนอของ Finnhouses โดยอัตโนมัติ
5. **การผ่านด้าน brand ไม่เท่ากับอนุมัติ publish:** ยังตรวจ `thai_language_incoherent`, `unverifiable_factual_claim` และ structural/dedupe guard ตามเดิม ตัวเลขราคา/ปี/การรับประกันต้องมีข้อมูลรองรับหรือระบุว่าเป็นประมาณการพร้อมสมมติฐาน ไม่อนุญาตให้ใส่คำว่า “ประมาณ” เพื่อผ่านทุก claim
6. **ข้อกำหนดหลักฐานสำหรับการบล็อกด้าน brand:** ผู้ตรวจต้องระบุข้อความจริงที่ทำให้เข้าใจว่าบริษัทรับจ้างสร้างบ้าน พร้อมอธิบายบทบาท/ข้อเสนอที่ผิด ห้ามสร้างประโยคหลักฐานขึ้นเองหรืออ้างแค่ชื่อหมวด หากหาหลักฐานไม่ได้ ห้ามใส่ reason นี้; ตรวจเกณฑ์อื่นต่อไป
7. **นโยบายเดียวตลอดสาย:** writer, rewriter และ Quality Gate ต้องรับขอบเขตเดียวกันจาก Business Model และ ADR นี้ ไม่แก้เฉพาะ reviewer แล้วปล่อยให้ writer สร้างข้อเสนอรับสร้างบ้านต่อไป

#### การนำไปใช้และเกณฑ์ยืนยันผล

- Export **workflow ที่ active จริง** ก่อนแก้ ระบุ workflow ID/version และสำรองฉบับเดิม; repo ณ วันที่ตรวจมีเพียง README ใน `memory/n8n-workflows/` ไม่มี JSON ของ WF1 จึงยังยืนยัน prompt/runtime ปัจจุบันไม่ได้
- ปรับ writer/rewriter/gate ตามนโยบายนี้ ทดสอบบทความเต็มของกรณีข้างต้นในทางเดินที่ไม่ publish และเพิ่มเคสภาษาผิด/claim ไม่มีหลักฐานที่ต้องยังถูกบล็อก
- รอบนี้เป็น policy amendment เท่านั้น ไม่เปลี่ยน contract `{pass, reasons[]}`, enum เหตุผล, parser, fail-open infra policy, feedback API หรือ database schema โดยปริยาย หากเพิ่ม field หลักฐาน/policy version ใน runtime ต้องปรับ parser/log ที่เกี่ยวข้องและทดสอบแยกก่อน deploy
- ก่อน activate: เคสผ่านด้าน brand ต้องไม่ถูกบล็อกด้วย `brand_guardrail_violation`; เคสข้อเสนอรับจ้างโดยตรง/โดยนัย/CTA ต้องถูกบล็อกครบ บันทึก expected/actual กับข้อความหลักฐาน ไม่ถือว่าตารางตัวอย่างคือผลทดสอบจริง
- หลัง activate: บันทึกเวลาเริ่มใช้และ workflow version แยกผลก่อน/หลัง นำบทความเก่าที่มีต้นฉบับมา replay โดยไม่ publish และให้มนุษย์ตรวจซ้ำตามนโยบายใหม่ โดยเก็บ feedback เดิมไว้ ไม่ reset หรือแก้ย้อนหลังเพื่อทำให้เปอร์เซ็นต์สูงขึ้น
- Dashboard API ปัจจุบันอ่านล่าสุดไม่เกิน 200 rows (`app/api/quality-gate/accuracy/route.ts`) จึงไม่ควรอ้าง accuracy ตลอดอายุระบบเมื่อข้อมูลเกินขอบเขตนี้; เก็บข้อจำกัดนี้ไว้ในการประเมินหลังแก้
- **เกณฑ์ปิดงาน runtime:** เห็น active workflow ใช้นโยบายใหม่ + ผลทดสอบทั้ง pass/block และภาษา/claim + execution จริงหลังเปลี่ยน จึงรายงานได้ว่าการแก้มีผลใน production การ merge เอกสารอย่างเดียวไม่เปลี่ยนพฤติกรรม n8n

**Context**: ต่อจาก Phase 1 (QC Accuracy Dashboard, ADR-015) และบทสนทนา reflective เรื่อง "ระบบพิสูจน์ตัวเองว่าทำงานถูก" — ตรวจสอบพบว่า WF1 (Blog auto-publish) มี "Publish Guard + Dedupe History" node อยู่แล้ว แต่เช็คแค่**โครงสร้าง**ล้วนๆ (ความยาว title/slug ≥ ค่าที่กำหนด, มี FAQ schema, ไม่มี `<h1>` ซ้ำ, slug ไม่ซ้ำ ฯลฯ) — **ไม่มีการเช็คเนื้อหาจริงเลยแม้แต่จุดเดียว** ว่าตรงกับโมเดลธุรกิจจริงหรือไม่, มีคำที่ห้ามพูด (เช่น อ้างว่า Finnhouses รับสร้างบ้านเอง — discontinued ตาม ADR-010) หรือไม่, ภาษาไทยเพี้ยน/ตัดกลางคำแบบที่เจอใน ISSUE-016 หรือไม่ — engine publish อัตโนมัติทุกวันโดยไม่มีใครอ่านเนื้อหาก่อนเลย

ถาม Archi ผ่าน AskUserQuestion 2 ข้อก่อนแก้: (1) อยากให้ gate เช็คเรื่องอะไร → เลือก **ทั้งหมด** (brand guardrail + ภาษาไทยสมบูรณ์ + ความถูกต้องเชิงข้อเท็จจริง) (2) ถ้าไม่ผ่านให้ทำอะไร → เลือก **บล็อกอัตโนมัติ + แจ้งเตือน** (เหมือน Publish Guard เดิม ไม่ auto-retry เพื่อกัน infinite loop)

**Decision**: เพิ่ม 4 node ใหม่เข้า WF1 (`Finnhouses WF1 — Article + Publish (10_ai_quality_gate).json`) โดยไม่แก้ node เดิมเลยแม้แต่บรรทัดเดียว (ยกเว้นจุดต่อสาย/reposition คอสเมติก):
1. **AI Quality Gate** — เรียก `@n8n/n8n-nodes-langchain.openAi` (gpt-4o-mini, credential เดิม `OpenAI account` ที่ WF1/WF2 ใช้อยู่แล้ว) fan-out ขนานจาก "Prepare Post Payload" (สาขาที่ 3 นอกจาก "Check Existing Post by Slug" กับ "Publish Guard + Dedupe History" เดิม) ส่ง title/slug/content เข้าไปให้ตรวจ 3 เงื่อนไข: `brand_guardrail_violation`, `thai_language_incoherent`, `unverifiable_factual_claim` — บังคับ prompt ระบุ business model จริง (นายหน้า + Fix & Flip + ที่ปรึกษาตรวจสอบ ไม่ใช่ผู้รับเหมา) ตอบกลับ JSON ล้วน `{pass, reasons[]}`
2. **Parse AI Gate Result** (Code) — parse JSON output, **fail-open ถ้า parse error/AI เรียกไม่สำเร็จ** (ไม่บล็อกเพราะ gate เองมีปัญหา infra — ป้องกันไม่ให้ AI API ล่มแล้วบล็อก queue ทั้งหมดเงียบๆ) fail-closed เฉพาะตอนโมเดลตอบ `pass:false` จริงเท่านั้น
3. **Merge Guards** (n8n Merge, combineByPosition) — รวม output ของ "Publish Guard + Dedupe History" (เดิม) กับ "Parse AI Gate Result" (ใหม่) เข้าด้วยกัน
4. **Combine Guards** (Code) — รวม `publish_guard_reasons` (structural) + `ai_gate_reasons` (AI) เป็น array เดียว คง field name `publish_guard_ok`/`publish_guard_reasons` เป๊ะตามเดิม — ทำให้ "IF Publish Guard Passed", "Blocked Log", "Notify Hub Blocked" **ไม่ต้องแก้เลยแม้แต่บรรทัดเดียว** เพราะยังอ่าน field เดิมที่ชื่อเดิมอยู่

**สิ่งที่พบระหว่างทาง (ไม่ได้แก้ในรอบนี้ — flag ไว้)**: "Check Existing Post by Slug" (WP dedupe lookup) ไม่มีการต่อสายเข้าที่ไหนเลยใน `connections` graph ของไฟล์ 9_queue_sync_fix ที่ใช้งานจริงตอนนี้ — แปลว่า `duplicate_slug_exists` ใน Publish Guard เดิมน่าจะไม่เคย fire จริง (เพราะ `items[1]` ที่โค้ดอ้างถึงไม่มีทางมีข้อมูลจากสายที่ขาดหายนี้) เป็น latent bug ที่มีมาก่อนรอบนี้ ไม่เกี่ยวกับ Phase 2 — ต้องยืนยันใน n8n canvas จริงก่อนแก้ (ไฟล์ static อ่านได้แค่ระดับนี้)
