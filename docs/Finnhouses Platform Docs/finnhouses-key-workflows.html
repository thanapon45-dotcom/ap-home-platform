Workflow หลักและจุดตรวจ

แยกการประสานงานจากโค้ดออกจากลำดับ node ที่ต้องยืนยันใน n8n

ทบทวน 22 กันยายน 2026 · อ้างอิง main 1dddb46

เอกสารทั้งหมดภาพรวมสถานะ
ยืนยันเส้นทางจากโค้ดและ ADR ณ commit ที่ระบุ การมีโค้ดไม่ยืนยันว่า deployment, credentials และ workflow ที่ active ทำงานครบแล้ว รอบนี้ไม่ได้รันงาน production

WF1 · บทความและ Quality Gate

ADR-016 แก้ขอบเขต brand แล้วใน PR #3: บทความให้ความรู้สร้างบ้านผ่านได้; บล็อกเมื่ออ้างบริการรับจ้างสร้างบ้านหรือ CTA ที่สื่อเช่นนั้น ยังต้องตรวจภาษา ข้อเท็จจริง โครงสร้างและเนื้อหาซ้ำ

ยังต้อง export workflow ที่ active เพื่อตรวจ writer / rewriter / gate และรันทดสอบทั้งกรณีผ่านและบล็อก การ merge เอกสารไม่แก้ prompt ใน n8n อัตโนมัติ Policy เดิมใน ADR ยังให้ AI infrastructure/parse error เป็น fail-open ซึ่งต้องแยกจากการตรวจเนื้อหาผ่านจริง

01 · ผู้ใช้สั่งผ่าน /marketing หรือ schedule ที่ตั้งใน n8n
02 · Next.js proxy เรียก Hub /action/blog/queue/run-next; Assistant ใช้ /action/blog/run เมื่อระบุ keyword
03 · Hub เรียก WF1; ลำดับ writer/guard/gate ต้องตรวจ active export
04 · ทางผ่านเผยแพร่ WordPress; ทางบล็อกแจ้งเหตุผล; callback กลับ Hub ต้องสัมพันธ์ run ID
05 · ตรวจ quality_gate_log และ human feedback แยกจากเพียงสถานะ execution สำเร็จ

Accuracy = feedback ที่ถูก ÷ แถวที่มี feedback; endpoint อ่านล่าสุดไม่เกิน 200 decisions และแสดง headline เมื่อมี feedback ≥10 ครั้ง False positive คือบล็อกผิด ส่วน false negative คือปล่อยผ่านผิด ตัวเลข 53.2% จากผู้ใช้เป็น snapshot ก่อนแก้ ไม่ใช่ผลหลังแก้

WF2 · ภาพและการอัปเดตบทความ

ตาม ADR / บันทึก workflow: WF1 ส่งงานภาพไป WF2 แล้วอัปเดต WordPress และ callback /webhook/image-done กลับ Hub ต้องตรวจ provider, fallback, guard และ connection จาก active export ไม่ถือว่าเส้นทาง /api/image ของ Content Studio เป็น workflow เดียวกัน

Facebook

01 · AI Content เรียก /api/chat และ /api/image ตามงานที่เลือก
02 · ผู้ใช้ตรวจข้อความ รูป และข้อมูลก่อนสั่งเผยแพร่
03 · โพสต์ทันที: /api/fb/publish → FB Backend → Facebook
04 · Queue: /api/fb/queue/* → Hub v1 → กลไกเผยแพร่ของ queue
05 · ตรวจผลโพสต์จริงก่อน retry ไม่อนุมานว่ารับ request แล้วโพสต์สำเร็จ

Seller intake และ Property Review

01 · LINE seller intake เป็น integration ตามเอกสารเดิม ต้องตรวจ webhook/active revision
02 · เมื่อมี properties รอตรวจ Dashboard อ่าน /api/property/pending
03 · เจ้าของระบบตรวจข้อมูลและ upload ภาพ จากนั้น /api/property/publish → Hub → WordPress
04 · ตรวจสถานะและ URL จริงหลังเผยแพร่

QC LINE

01 · LINE/n8n รับภาพตาม integration ที่ตั้งอยู่ แล้วส่งไป Hub QC ingest
02 · Hub เรียก AI และเก็บผลตรวจใน qc_inspections; ไม่รับรองเวลาคงที่
03 · มนุษย์ตรวจผลและส่ง feedback ผ่าน workflow ไป /api/qc/feedback
04 · Dashboard QC Accuracy อ่านข้อมูลประเมินผ่าน /api/qc/accuracy; การมี feedback ไม่เท่ากับ model เรียนรู้เอง

Market Intelligence

01 · ผู้ใช้ส่ง text / area / timing ผ่าน /api/market-intel
02 · Next.js ส่งต่อ webhook ของ n8n ตาม env
03 · Collector ตาม ADR เขียน market_insights, buyer_context_signals, content_frames และส่งผลตาม workflow
04 · ตรวจ execution และข้อมูลที่เขียนจริง; Brains อ่านต่อเมื่อมี record แล้ว
05 · Human calibration บันทึกความถูก/ผิด ไม่ได้ retrain อัตโนมัติ

Schedule / Wake-up / Parser / Performance

เวลา cron, timezone, workflow ID, revision และ credentials ต้องอ่านจาก n8n ที่ active งาน CRM Note Parser และ FB Performance Tracker ที่เคยระบุว่า LIVE ในเอกสารเก่าไม่ได้รับการยืนยัน runtime รอบนี้ ห้ามใช้ชื่อไฟล์ export หรือวันที่เดิมรับรองว่าทำงานอยู่ทุกวัน

เมื่อ workflow ผิดพลาด

01 · เก็บ run ID, execution ID, เวลาที่เกิดและ node ที่ผิดพลาด
02 · เทียบ input/output และข้อมูลปลายทางก่อน retry เพื่อป้องกันการเผยแพร่ซ้ำ
03 · แก้และทดสอบในขอบเขตงานนั้นก่อน activate; บันทึก revision และผล pass/block ให้ย้อนตรวจได้
