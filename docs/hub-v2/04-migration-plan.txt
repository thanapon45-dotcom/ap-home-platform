================================================================================
  AP-HOME HUB v2  |  Document 4/5  |  Migration Plan
  แผนย้ายระบบจาก server.cjs (v1) → Hub v2 (TypeScript Clean Architecture)
  Strategy: Incremental — ไม่ Big Bang, v1 ต้องทำงานได้ตลอดการ migrate
================================================================================

CORE CONSTRAINT (ห้ามละเมิด)
  ✗  ห้าม remove server.cjs ก่อน cutover
  ✗  ห้าม break endpoint เดิมแม้แต่ endpoint เดียว
  ✗  ห้าม deploy code ที่ยังไม่ผ่าน smoke test
  ✓  v1 และ v2 อยู่ร่วมกันได้ตลอด Phase 1-4

================================================================================
  1. OVERVIEW — MIGRATION PHASES
================================================================================

  Phase    ชื่อ                    ระยะเวลา   เป้าหมาย
  ─────────────────────────────────────────────────────────────────────────────
  Phase 0  Scaffold                1 วัน      สร้างโครงสร้าง TypeScript ว่าง
  Phase 1  Core + Shared           2 วัน      Domain, Ports, Shared utils
  Phase 2  Infrastructure          2 วัน      Adapters (Supabase, Telegram, n8n)
  Phase 3  Modules + Use Cases     3 วัน      Business logic ทั้งหมด
  Phase 4  Presentation            2 วัน      Routes + Controllers
  Phase 5  Parallel Run            3 วัน      v1 + v2 ทำงานพร้อมกัน → verify
  Phase 6  Cutover                 1 วัน      switch traffic → v2, remove v1
  ─────────────────────────────────────────────────────────────────────────────
  TOTAL                           ~14 วัน    (working days — ไม่รวม buffer)

  7. PHASE 5 — PARALLEL RUN  (3 วัน)
================================================================================

  เป้าหมาย: v1 + v2 ทำงานพร้อมกัน เทียบผลลัพธ์ก่อน cutover

  Setup:
  [ ] v1 (server.cjs) → PORT=3000 (production traffic)
  [ ] v2 (server.ts)  → PORT=3001 (shadow traffic)
  [ ] Railway: deploy v2 เป็น separate service ชื่อ "hub-v2-shadow"

  Verification Checklist:
  [ ] Blog run → v2 ทำงาน end-to-end ได้เหมือน v1
  [ ] Blog reset → ทั้งสองตอบ 200
  [ ] QC ingest → vision result ใกล้เคียง v1 (± 10% score)
  [ ] FB build-queue + run-queue → v2 publish ได้จริง
  [ ] Health Monitor → Telegram alerts ส่งถูกต้อง ไม่ duplicate
  [ ] State → /api/state ข้อมูลตรงกันทั้ง v1 และ v2
  [ ] Error handling → 409, 401 ตอบ format เดียวกัน
  [ ] Rate limit → ทดสอบ > 60 req/min → 429

  Monitor 3 วัน:
  [ ] ไม่มี unhandled exception ใน v2 logs
  [ ] Cost per AI request ไม่เกิน budget
  [ ] Memory ไม่ leak (heapUsed stable หลัง 24h)

  ✅ Done when: ทุก checklist item ผ่าน ไม่มี regression


================================================================================
  8. PHASE 6 — CUTOVER  (1 วัน)
================================================================================

  เป้าหมาย: switch traffic ทั้งหมดไปที่ v2 อย่างปลอดภัย

  Pre-cutover (ตรวจก่อน):
  [ ] v2 health check: GET /api/health/detailed → overall: "healthy"
  [ ] Supabase มี backup ล่าสุด (< 1 ชั่วโมง)
  [ ] แจ้งทีมว่าจะมี maintenance window 15 นาที

  Cutover Steps:
  1. [ ] Set v2 PORT=3000 ใน Railway env vars
  2. [ ] Set v1 PORT=3099 (ยังอยู่ แต่ไม่รับ traffic หลัก)
  3. [ ] Redeploy v2 service
  4. [ ] ทดสอบ production: POST /action/blog/run → 200
  5. [ ] Monitor Telegram alerts 30 นาที — ต้องไม่มี unexpected alert
  6. [ ] ถ้าปกติ → ประกาศ cutover สำเร็จ

  Rollback Plan (ถ้ามีปัญหาภายใน 30 นาที):
  1. [ ] Set v1 PORT=3000 → Redeploy v1
  2. [ ] Set v2 PORT=3001
  3. [ ] แจ้ง Telegram: "Hub v2 cutover rolled back"
  4. [ ] เปิด issue → fix → repeat Phase 5

  Post-cutover (หลัง 48 ชั่วโมง ถ้าไม่มีปัญหา):
  [ ] Remove server.cjs จาก repo
  [ ] Update Railway service เป็น hub-v2 (rename)
  [ ] Archive hub-v2-shadow service
  [ ] อัพเดท documentation

  ✅ Done when: v2 รัน production 48h ไม่มี rollback

================================================================================
  10. ROLLBACK TRIGGER CONDITIONS
================================================================================

  ให้ rollback ทันทีถ้าเกิดอย่างใดอย่างหนึ่ง:
  - Error rate > 5% ใน 10 นาทีแรกหลัง cutover
  - Blog run ไม่ trigger n8n ใน 3 ครั้งติดต่อกัน
  - QcIngest ส่ง Telegram alert ผิดพลาด > 2 ครั้ง
  - /api/health/detailed → overall: "unhealthy"
  - Memory leak: heapUsed เพิ่ม > 200MB ใน 1 ชั่วโมง
  - ทีมรายงาน bug ที่ไม่มีใน v1
